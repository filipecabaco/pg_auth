# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

Primary: teams building applications on Postgres with no backend of their own, typically Supabase
or PostgREST called straight from a browser or mobile app. Their app needs real authorization
(sharing, teams, roles, inherited folders, rules on a row's own fields) and they do not want to run
an API server just to check permissions, nor hand-write and maintain row level security policies
for every table.

Secondary (not the page's lead): teams already running OpenFGA, SpiceDB or Cerbos who want the
database to enforce the same decisions for every client.

## Product Purpose

pg_auth is a Postgres extension (Postgres 15 to 18) and a sidecar. An authorization engine
(OpenFGA, SpiceDB, Cerbos or Cedar) decides who may see and change each row; Postgres enforces that
decision for every client as row level security. The setup is the engine's rules in its own
syntax, stored with `authz.set_rules` beside a YAML mapping that protects tables and makes rows
relationships, so access is granted and revoked by writing rows (delivered to the engine through
an outbox), and `authz.why` / `authz.doctor` explain a hidden row or a broken
setup. Success: an app with no backend gets authorization it would otherwise need a service for,
with less to write and nothing to keep in sync by hand.

## Positioning

The engine's model is the single place access rules live, and Postgres enforces it directly: no
backend in the request path, no per-table policy code, and grants written as ordinary rows through
the same API the app already uses. It explains itself (why a row is hidden, what in the setup is
wrong), where hand-written RLS fails silently.

## Operating Context

Evaluated by developers reading the landing page and README, trying the in-browser demo, then
building from source against their own Postgres with a sidecar next to it. The site is MkDocs
Material with a custom home template (`overrides/home.html`, `docs/stylesheets/home.css`), deployed
to GitHub Pages from `filipecabaco/pg_auth`.

## Capabilities and Constraints

- Engines: OpenFGA and SpiceDB (relationships), Cerbos (attribute rules compiled into SQL filters).
- Subjects from a JWT claim (as Supabase/PostgREST set it), a verified bearer token, or a setting.
- Reads, writes, inserts checked on a parent, several ways to reach a row, inherited trees, key
  expressions; relationship tables for grants; fails closed when the engine cannot answer.
- Needs `shared_preload_libraries`: servers you control, or managed Postgres only where the provider
  preloads it. The sidecar runs beside Postgres on a Unix socket, or on another host over HTTPS with
  signed requests and answers.
- Status: experimental, pre-release, built from source; no license chosen yet. State this plainly.

- Benchmarks set expectations about cost. They are never framed as RLS being slow.

## Evidence on Hand

- Live, in-browser demo built with snowglobe (as `../pg_redis` does), running Postgres with
  pg_auth, the sidecar and all four engines (Cedar inside its sidecar); the larger download is accepted.
- `bench/docker` results (35 scenarios, 489 pairs, 2026-10-29): 0.80x of best-practice RLS time
  overall (measured with OpenFGA); per-scenario figures in `docs/benchmarks.md`.
- Correctness: parity against each engine (`compare/`), 96.8% combined line coverage, CI on
  Postgres 15 to 18; the RLS issues catalogue with a verdict per scenario.
- Relationship tables: grants and revocations visible 4 to 34 ms after commit (`compare/relationships.exs`).
- No users, customers, testimonials or production deployments: never imply any.

## Product Principles

1. Usability first: less to write, one place for rules, and errors that explain themselves.
2. No backend required: everything a Postgres-backed app needs happens in the database and the
   engine.
3. Honest about status and limits: experimental, and what it shares with RLS stated as plainly as
   what it fixes.
4. Benchmarks set expectations; they are not the pitch.
