Your app's permissions, enforced by Postgres. No backend.

Your app talks to Postgres directly, through an API like PostgREST, with no server of its own. pg_auth makes Postgres show each user only the rows they may see. Below, Anne and Bob use the same app, and Anne gives Bob access by writing one row.and Bob sees a document once Anne publishes it.

The rules live in an authorization engine (here OpenFGA), in its own syntax. A few lines of YAML stored beside them protect the documents table:

type document
  relations
    define viewer: shared_with or can_read from org
# the mapping
documents: {read: viewer, write: editor}
definition document {
  permission viewer = shared_with + org->can_read
}
# the mapping
documents: {read: viewer, write: editor}
resourcePolicy:
  resource: document
# the mapping
documents: {read: view, write: edit, attributes: [owner, status]}
entity Document { org: Org, admins: OrgAdmins };
permit (principal, action == Action::"view", resource)
  when { principal in resource.org };
# the mapping
documents: {read: view, write: edit, attributes: [org_id as org, org_id as admins]}

The rules: an organisation's members read its documents, and only its admins edit them. Anne is the admin of org 1, which owns three documents. Bob is in no org yet.

The rule: everyone reads published documents and their own drafts, and only the owner edits. Anne owns three documents, one of them published.

How it works with no backend

Runs where you configure Postgres yourself: the extension loads when Postgres starts, which RDS, Cloud SQL, Neon and hosted Supabase do not allow. A small service, the sidecar, runs beside Postgres or on another host over HTTPS. Experimental, pre-release, no license yet. The demo downloads about 150 MB once.

select authz.set_rules('cerbos', 'resource/document', $$
apiVersion: api.cerbos.dev/v1
resourcePolicy:
  version: default
  resource: document
  rules:
    # anyone signed in reads published documents and their own drafts
    - actions: ["view"]
      effect: EFFECT_ALLOW
      roles: ["authenticated"]
      condition:
        match:
          any:
            of:
              - expr: request.resource.attr.owner == request.principal.id
              - expr: request.resource.attr.status == "published"
    # only the owner edits
    - actions: ["edit"]
      effect: EFFECT_ALLOW
      roles: ["authenticated"]
      condition:
        match:
          expr: request.resource.attr.owner == request.principal.id
$$, mapping => $$
documents:
  read: view
  write: edit
  attributes: [owner, status]
$$);

select authz.set_rules('cedar', 'documents', $$
// The demo's policies in Cedar, stored as the rule named `documents` beside the schema. pg_auth
// turns each into a filter on the table: `principal in resource.org` becomes `org_id IN (the
// subject's orgs)`, `principal in resource` the ids of the documents shared with them.

// an org's members read its memberships; its admins, who are members too, change them
permit (principal, action == Action::"read", resource is Org) when { principal in resource };
permit (principal, action == Action::"manage", resource is OrgAdmins) when { principal in resource };

// a document is read by its org's members and by whoever it is shared with
permit (principal, action == Action::"view", resource is Document) when { principal in resource.org };
permit (principal, action == Action::"view", resource is Document) when { principal in resource };

// and written, or shared, by its org's admins
permit (principal, action == Action::"edit", resource is Document) when { principal in resource.admins };
$$);

The rules stay in the engine's own syntax, and the sidecar gives them to OpenFGA as they are; pg_auth reads only the mapping. Each table in it gets a plain RLS policy that asks the engine, so pg_policies lists it.

How it works

Four parts, two of them yours already. Your app sends ordinary SQL; pg_auth asks the engine who may see what, through a sidecar beside Postgres or on its own host, and turns the answer into a filter Postgres can use an index for.

Your app browser or phone, through PostgREST: no server of its own
select * from documents as bob, from the request's token
insert into memberships as anne
Postgres + pg_auth row level security, planned by pg_auth
which documents may bob view? Unix socket or signed HTTPS; answers cached, refreshed ahead
outbox row written in the same transaction
Sidecar beside Postgres or on its own host: cache, delivery, the engine's credentials
ListObjects · LookupResources · PlanResources · Cedar's partial evaluation HTTP
write the relationship then every session asks again
Engine OpenFGA, SpiceDB or Cerbos, with your rules in its own language; or Cedar, which the sidecar runs itself
  1. Reading. The answer comes back as the ids bob may see (for Cerbos and Cedar, a condition on the row's fields), and pg_auth plans the query as id = any('{1,2,3}') on the table's index. Every client gets the same rows: PostgREST, a script, psql.
  2. Granting. A row in a relationship table is a grant. A rolled-back write never reaches the engine; if the engine is down, grants wait and are delivered later.

Write each rule once, not in every table

Who may read a document? Members of its organisation, and anyone it was shared with. Here is that one rule, both ways.

Row level security, by hand

A policy per operation, on every table that needs the rule.

create policy read on documents
  for select to authenticated
  using (
    exists (select 1 from memberships m
            where m.org_id = documents.org_id
              and m.user_id = (select auth.uid()))
    or exists (select 1 from shares s
               where s.doc_id = documents.id
                 and s.user_id = (select auth.uid())));
-- then update, insert and delete,
-- and again for comments, files, …

pg_auth

  1. Say who is a viewer, once, in the engine's model:

    type document
  relations
    define org: [org]
    define shared_with: [user]
    define viewer: shared_with or member from org

  2. Name the table it protects, in the mapping stored beside it:

    documents:
  read: viewer

Sharing with a team or adding a role is a change to the model, or a row in a table: there is no policy to edit. The model lives with your migrations: authz.set_rules stores it with its mapping, which protects the tables; the sidecar sends the model to the engine, and a mapping naming a permission the model does not define fails to commit. The rules and their mapping

Ask why a row is hidden

Row level security (Postgres's per-row access rules) hides rows without a word. authz.why says who Postgres thinks is asking, and which permission is missing. In the demo's data, after Anne added Bob to org 1, a database administrator asks why Bob still cannot see document 4, which belongs to org 2: 

select * from authz.why('documents', '4', as_subject => 'user:bob');
stepokdetail
subjectyesuser:bob (pg_auth.as_subject: an administrator acting as this subject)
row level securityyeson, forced: the table owner is checked too
rowyesid = 4 exists
policy pg_authnouser:bob lacks document#viewer on document:4; writes need document#editor
verdictnohidden from user:bob: no pg_auth policy allows it

Postgres's answer, with its t and f shown as yes and no. authz.doctor() checks the whole setup and prints the statement that fixes each problem. Inspect and debug

The row level security mistakes you cannot make

A view that leaks
Policies are forced on the table's owner, and the subject comes from the request, not the role running the query.
Policy recursion (42P17)
pg_auth's policy reads only the row, so it cannot recurse into another table's policies.
A partition queried directly
Every partition gets the policy, including ones created later.
A writer who cannot find their own rows
By hand, an update with no matching read policy silently changes 0 rows. Read and write permissions are installed together, so whoever may write a row can find it.
A spoofed identity
The request cannot set its own subject, and with no subject there are no rows.
An engine that is down
Queries fail: no row is shown when nobody can answer for it.

What it shares with row level security, where Postgres sets the rules: superusers and BYPASSRLS roles skip every policy, and so does a SECURITY DEFINER function they own. An identity set for a whole session on a pooled connection outlives its request; set it with SET LOCAL, as PostgREST does. Every issue, checked

What to expect

A protected query costs about what a well-written policy does

Overall, {{ '%.2f' | format(bench.ratio) }}x the time of a best-practice policy, planning and execution together: {{ bench.scenarios }} scenarios taken from problems people hit with row level security, {{ bench.pairs }} query and subject pairs, measured with OpenFGA (0.93x with SpiceDB; 0.69x with Cerbos and 0.79x with Cedar on the scenarios their rules express). Statements that finish in well under a millisecond pay for pg_auth's planning work, so expect those to take somewhat longer. A rule on a row's own values (a report's level against a reader's clearance) is checked row by row on OpenFGA: fine for reads by key, slow for scans.

A grant written as a row shows within tens of milliseconds

A membership or a share written as a row showed to its subject 4 to 34 ms after the commit, measured against OpenFGA and SpiceDB: pg_auth tells every session to ask again. A share with an end date disappears 60 to 120 ms after it ends. A change made in the engine itself, outside Postgres, shows once the engine's own reads see it (up to 5 s on SpiceDB's default consistency, 10 s with OpenFGA's caches on) and the sidecar's one-second cache has passed. How fresh answers are

When the engine or the sidecar is down, queries fail

Statements on protected tables fail rather than guess: at once if the engine refuses the connection, after 4 seconds if it hangs, after 5 if the sidecar does (both configurable). Answers cached in the last second still serve, and with the engine down, subjects too broad to list keep their last set in the permission index. Grants written as rows wait and are delivered when it is back.

It needs a Postgres you configure

Postgres 15 to 18 with pg_auth in shared_preload_libraries: a VM, Docker, Kubernetes, self-hosted Supabase. Not RDS, Cloud SQL, Neon or hosted Supabase, which do not preload extensions; running the sidecar over HTTPS does not change that. The sidecar runs beside Postgres on a Unix socket, or on another host over HTTPS, where every request and answer is signed with a secret Postgres and the sidecar hold. Install

It is experimental

Pre-release, built from source, no license chosen yet. Every engine is checked for parity against its own answers, and the tests run on Postgres 15 to 18. How it is tested

Pick the engine that fits your rules

EngineDecides onGood for
OpenFGArelationshipsSharing, teams, orgs, folders: who is related to what. Conditions on the request (a region, the time) and grants that end.
SpiceDBrelationshipsThe same model, with SpiceDB's schema and consistency. Caveats, including on the row's own values, and grants that end.
Cerbosthe row's fields and the user's rolesOwners, statuses, departments: rules over attributes. A tenant's own policies (scopes).
Cedarthe row's fields, and the groups and folders above itPolicies over attributes and hierarchies (principal in resource.org), run inside the sidecar: no engine server to operate.

Postgres speaks one small protocol to a sidecar, on a Unix socket or over HTTPS, so changing engines does not touch the database.

Try it on your own Postgres

Build the extension, preload it, run the sidecar pointed at your engine (beside Postgres, or on its own host over HTTPS), and store your rules with a mapping naming the tables they protect.
