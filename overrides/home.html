PostgreSQL extension · Rust + pgrx · PG 15–18

Authorization, enforced by Postgres.

pg_auth turns an authorization engine's decisions into row level security. Model who may see what in the engine, and every client that reaches Postgres (PostgREST, your API, a psql session) reads only the rows its subject may see. The planner shapes each protected scan with the engine's answer, so checking costs about what a hand-tuned policy does.

Three ways to check a scan

At planning, pg_auth asks the sidecar once per protected table which objects the subject may access, and picks the plan from the answer. authz.explain(query) says which one a query gets, and why.

One call per table

Point a table at an object type and a permission. pg_auth installs ordinary RLS policies, forced, on every partition now and later, and its planner hook turns them into an indexable filter or a batched check. Several ways to reach a row, inserts checked on the parent, keys that are expressions and trees the app already stores are arguments, not hand-written SQL.

Protecting tables 
-- a comment is visible to whoever may view its document
select authz.protect('app.comments',
       'document', 'document_id', 'viewer');

-- a storage path's first folder names the project
select authz.protect('storage.objects', 'project', null,
       'viewer', p_key => 'split_part(name, ''/'', 1)');

-- a stored folder tree: the engine lists direct grants,
-- Postgres expands them through a closure it maintains
select authz.protect('app.folders', 'folder', 'id', 'viewer',
       p_hierarchy => 'app.folders(id, parent_id)',
       p_direct    => 'viewer_direct');

Built for every surface that reaches Postgres

Every client

The policies are ordinary RLS, so PostgREST, GraphQL, Storage, Realtime, application servers and psql all read through them. No authorization left in the app.

Supabase subjects

The subject is a JWT claim as PostgREST sets it, a bearer token verified against a JWKS, or a setting only a trusted role may set. No subject, no rows.

Broad subjects

An admin who sees most rows reads from the permission index or in ordered batches, and a cached plan is rebuilt when a subject of another breadth reuses it.

Writes

Updates and deletes by broad subjects find their rows through the index set. Inserts can be checked on the parent object. Without a write permission, writes are denied.

Advice

authz.explain names each table's path and why; authz.last_statement_advice() says where the engine had to check rows and how to stop it; authz.lint() scores hand-written policies.

Fails closed

An unreachable sidecar, an engine error or a malformed answer fails the statement. The settings that steer decisions are superuser-only, and unsafe Rust stays in two modules.

A parity suite runs every scenario's queries as each subject and compares the rows with the engine's own answers, including cached plans reused across subjects. How parity is checked

One protocol, any engine

The extension never talks to an engine. It asks a sidecar on a local Unix socket three questions: which objects may this subject access, may it access these, and fill this subject's permission index. The sidecar translates them to the engine's API (OpenFGA's or SpiceDB's) and keeps the engine's credentials and network calls outside the database.

  • list answers with ids, or too_many past the engine's limit, which sends pg_auth to batched checks.
  • check answers a batch of ids in one round trip; missing answers are denials.
  • fill streams a broad subject's complete list into Postgres, kept fresh from the engine's change feed.
The protocol 
# one JSON object per line, over a Unix socket
> {"op":"list","subject":"user:anne",
   "permission":"viewer","type":"document"}
< {"ids":["1","2"],"engine_us":840,"valid_ms":500}

> {"op":"check","subject":"user:anne",
   "permission":"viewer","type":"document",
   "ids":["1","9"]}
< {"allowed":[true,false],"engine_us":1200}

> {"op":"ping"}
< {"engine":"spicedb"}

Install

The extension hooks the planner, so it has to be preloaded. Build it, preload it, run the sidecar next to Postgres, and point Postgres at the sidecar's socket.

Getting started 
# build and install into the active Postgres (15 to 18)
git clone https://github.com/filipecabaco/pg_auth && cd pg_auth
cargo pgrx install --release

# postgresql.conf, then restart
shared_preload_libraries = 'pg_auth'

# the sidecar, next to Postgres, asking SpiceDB (or OPENFGA_URL=...)
SPICEDB_URL=http://localhost:8443 SPICEDB_TOKEN=... \
  PG_AUTH_SOCKET=/run/pg_auth/authz.sock pg-auth-sidecar

# as a superuser
create extension pg_auth;
alter system set pg_auth.sidecar_socket = '/run/pg_auth/authz.sock';
select pg_reload_conf();

Good to know

  • It needs Postgres 15 to 18, shared_preload_libraries and a sidecar on the same host, so it runs on servers you control, and on managed Postgres only where the provider offers them.
  • The sidecar speaks OpenFGA and SpiceDB. The extension speaks the same small protocol to it whatever the engine and does not know which one is behind it, so another engine is a change to the sidecar, not to Postgres.
  • Answers are as fresh as the engine (OpenFGA's caches, 10 s; SpiceDB's default reads, up to 5 s behind), minus the sidecar's cache TTL (1 s by default). Writes to the engine and to the table do not commit atomically.
  • Row locks, inserts, and writes by broad subjects without a fresh index set check rows one at a time, from the index once it is fresh. Writes keep the per-row policy, since AuthzBatch does no EvalPlanQual rechecks.
  • For a declared hierarchy the app's table, not the engine's parent tuples, decides inheritance. pg_auth cannot verify that the model has the declared shape.
