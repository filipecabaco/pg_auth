# Prior art: making database-native row-level authorization fast (for pg_auth)

Legend: [V] = verified this session from a fetched primary source or Postgres source; [U] = UNVERIFIED (from memory / secondary source, confirm before relying).
Constraint from user: enforcement stays in the DB for all clients. No app-layer authz.

---------------------------------------------------------------------
## 0. How Postgres RLS actually plans (ground truth, from source)

- Policies are expanded in the rewriter (row_security_policy_hook is the extension point) into `RangeTblEntry.securityQuals`.
- planner.c [V] (master, src/backend/optimizer/plan/planner.c): `pull_up_sublinks(root)` runs at line ~886, on the jointree only. Later, in the "preprocess expressions" loop, each element of `rte->securityQuals` is run through `preprocess_expression(..., EXPRKIND_QUAL)` (line ~1174). That is after sublink pull-up, so `IN (SELECT ..)` / `EXISTS (...)` in a policy become SubPlans/hashed SubPlans, not semi-joins. This confirms the team's premise. Consequence: no join reordering, no semi-join/anti-join strategies, no parameterized index nested loop from the policy subquery.
- Comment in planner.c [V]: "child tables don't have their own securityQuals" -> for inheritance/partitions only the parent RTE's policies apply (when queried via parent); child policies are NOT applied via parent. (Docs page ddl-rowsecurity did not mention partitioning at all [V]; behaviour per source comment + memory of docs of CREATE POLICY [U].)
- indxpath.c [V]: line ~2605 `if (!restriction_is_securely_promotable(rinfo, index->rel))` -> user quals with a higher security_level than the rel's min can only be index quals if leakproof. This is the mechanism behind "non-leakproof user quals don't use my index when RLS is on".
- Tom Lane "Improving RLS planning" (2016) [V thread summary]: https://www.postgresql.org/message-id/tencent_B91D3F49695B5B5EFFC30B60236D8D47DA05@qq.com . Design = RestrictInfo.security_level; securityQuals go to baserestrictinfo (not subqueries); rule 1: index qual only if leakproof or level <= min level; rule 2: order_qual_clauses sorts by security_level then cost. That is what is in core now. Open item: security-barrier views are still never flattened (prepjointree.c line ~2015 [V]: not pulled up if rte->security_barrier).
- 2022 report (Zhao Rui) [V]: functional index `abc(a, lower(b))` only partially used for RLS role: `lower(b)` becomes a Filter, since `lower` is not leakproof. Workaround: plain column indexes / leakproof ops.
- Leakproof stats (Josh Kupershmidt doc patch, 2024) [V via search summary]: 387 builtin operators not leakproof vs 588 leakproof. https://www.mail-archive.com/pgsql-hackers@lists.postgresql.org/msg170516.html
- Andreas Lind thread "Per-role disabling of LEAKPROOF requirements for RLS?" (2025) [V via search summary, details not read]: https://www.mail-archive.com/pgsql-hackers@lists.postgresql.org/msg196470.html . Shows the community is still open to relaxing leakproof. Not committed as far as I know [U].
- Docs [V] https://www.postgresql.org/docs/current/ddl-rowsecurity.html : simplest and best-performing policy uses only the row's own columns; sub-SELECTs risk races/leaks; policies evaluated before user quals except leakproof functions.

## 1. Pain-point matrix (the four the user named)

### 1.1 Function calls in policies
Problems: (a) VOLATILE (default) functions re-evaluate per row and block index use / initplan hoisting; (b) SECURITY DEFINER or `SET`-clause functions are never inlined [V: https://wiki.postgresql.org/wiki/Inlining_of_SQL_functions, note it describes 8.4-9.5, re-verify against inline_function in clauses.c on PG17/18]; (c) non-leakproof functions in user quals; (d) plpgsql is opaque to the planner.
Prior art / fixes:
- Supabase: wrap in `(select auth.uid())` -> InitPlan evaluated once per statement. Benchmarks [V: https://github.com/orgs/supabase/discussions/14576], 100K rows: unindexed `auth.uid() = user_id` 179 -> 9 (units appear to be ms); `is_admin()` joined: 11,000 -> 7; `has_role()`: 178,000 -> 12; `team_id = any(array(select user_teams()))` 173,000 -> 16. 1M-row team example: `ANY(user_teams())` timed out >2 min; `ANY(ARRAY(select user_teams()))` 170 ms unindexed, 2 ms with team_id index. Index on user_id: 171 -> <0.1. `TO authenticated` on policy: 170 -> <0.1 for anon.
- Supabase docs [V]: security definer for lookups avoids nested RLS; `search_path=''`; keep in non-exposed schema. https://supabase.com/docs/guides/database/postgres/row-level-security
- SQL Server: predicate must be an inline TVF; optimizer expands it like a view [V that predicate = inline TVF; "expands like view" is U]. Docs best practice: avoid recursion, excessive joins, type conversions; SCHEMABINDING=ON skips per-user permission checks [V: https://learn.microsoft.com/en-us/sql/relational-databases/security/row-level-security].
- Oracle VPD: policy *function* returns a predicate string; cost is running that function at parse time. Policy types cache it [V from Oracle knowledge only; the fetched Oracle page did not contain the table, treat as U-but-well-known]: DYNAMIC (every execution), STATIC (once, cached in SGA), SHARED_STATIC, CONTEXT_SENSITIVE (re-run only when application context changes), SHARED_CONTEXT_SENSITIVE (cache shared across sessions/objects with same context). Docs: https://docs.oracle.com/en/database/oracle/oracle-database/19/dbseg/ (find "Policy Types").
  Key idea: the *predicate text* is generated at plan time from session context, so per-row work is just an ordinary predicate with bind values.
How pg_auth does it:
  * Generate predicates that are (i) inlinable-by-construction or (ii) plain expressions/subqueries over SQL-visible tables, never opaque plpgsql per row. In the row_security_policy_hook, build the qual node tree directly (like Oracle emitting text) instead of calling a function: e.g. `tenant_id = ANY(<array const>)` or `EXISTS(...)` with subject baked as a Const/Param.
  * Resolve the subject ONCE per statement: evaluate `current_setting('pg_auth.subject')` (or JWT claim) in hook, emit as Const when plan is custom (hook runs at rewrite so generic plans would bake it -> must mark the plan non-cacheable / invalidate on subject change; Oracle CONTEXT_SENSITIVE analog). Alternative: Param node (PARAM_EXTERN) so generic plans stay valid but InitPlan-hoist.
  * Mark the extension's own helper functions LEAKPROOF (requires superuser at install; only safe if they truly cannot error/leak) and STABLE/PARALLEL SAFE, so quals on them can be index quals and ordered early.

### 1.2 Joins inside policies / policies on joined tables / nested RLS
Problems: SubPlan (no pull-up, proven above); policy on lookup table (membership) triggers nested RLS on the lookup; per-row hashed subplan rebuilt per statement; join pushdown blocked by security barrier ordering.
Prior art:
- Tom Lane's 2016 example [V]: without policy `t1,t2 where pk1=fk and pk2=42` is an index nested loop; with a policy, seq scan on t1 + Filter. Fixed in PG10 for simple quals only; sublinks still not pulled up.
- Supabase: replace correlated join with `col in (select ... where user_id = auth.uid())` (uncorrelated -> hashed subplan once) [V]: 9,000 -> 20 ms (100K rows). Lists >~10K need more analysis [V].
- Snowflake [V https://docs.snowflake.com/en/user-guide/security-row-intro]: mapping-table policies are slower than simple expressions; suggestions: fewer lookups, co-locate mapping table, use *memoizable functions* (cache scalar-UDF result per query) to replace table lookup; protected objects become a `DynamicSecureView`; fewer policy arguments (bound columns are scanned even if unused); cluster on policy columns; metadata shortcuts (COUNT(*)) lost.
- SQL Server docs [V]: avoid excessive joins; no indexed views over RLS tables (lookups via the index would bypass the policy).
- Oracle RAS [U]: ACLs on data realms with a precomputed principal->privilege expansion kept in the DB; policies expressed as "realm = predicate", ACL evaluation becomes `ora_check_acl(...)` join. Not verified this session.
How pg_auth does it (ordered by impact):
  1. **Precompute subject->resource-set so the policy is a single indexed semi-join/ANY-array** (see section 5: materialized effective-permission tables, roaring bitmaps). Policy becomes `resource.id = ANY(<per-statement array>)` or `EXISTS (SELECT 1 FROM pg_auth.effective e WHERE e.subject = $subj AND e.res_type=.. AND e.res_id = t.id)`; the second is a SubPlan but each probe is an index lookup (O(log n)), the first is an InitPlan + ScalarArrayOp index scan (good below ~10-50K ids; verified order of magnitude by Supabase 16 ms/2 ms).
  2. **Do the sublink pull-up ourselves in the hook.** The hook runs at rewrite time, before the planner. For a SELECT we can instead add the join to `Query->jointree` / rtable ourselves? Not safely - changes row multiplicity and the security-barrier guarantees. Better: use `planner_hook`/`set_rel_pathlist_hook`/`set_join_pathlist_hook` to add a semi-join path; large effort. Cheaper trick: emit a `= ANY(ARRAY(subselect))` or hashed SubPlan form that the planner can already do index-scan on; and for the "driving from authorization" case emit `t.id = ANY(...)` which gives a Bitmap/Index scan driven from the permission set (the *reverse* direction vs per-row probe).
  3. **Avoid nested RLS on pg_auth's own tables**: tables owned by extension owner, no RLS enabled, access through the (non-inlinable but cheap) path or directly from the generated qual; Postgres applies RLS of lookup tables referenced in a policy qual for the *calling* user unless security definer, so don't use plain SELECT on RLS-enabled tables in generated quals.
  4. Possible core-patch direction (out of extension scope, flag as upstream opportunity): pull_up_sublinks for securityQuals followed by semi-join marked with security_level. Tom's thread [V] explicitly leaves this as later work.

### 1.3 Unindexed selects / seq scans caused by policy shape
Causes: (1) leakproof rule blocks index use of user quals (indxpath.c:2605 [V]); (2) policy col lacks index; (3) OR of permissive policies defeats single-index use (policies are ORed; BitmapOr only if each arm indexable); (4) function-wrapped columns (`lower(col)`); (5) poor selectivity estimates for SubPlans (planner uses default selectivity for `IN (subplan)` ~ hashed subplan estimates; stats don't see through SubPlan) [U on exact default numbers].
Prior art:
- Supabase [V]: index every policy column as leading btree column; composite PK (team_id,user_id) doesn't index user_id; explicit `.eq()` filters from client in addition to RLS to get index use (171 -> 9 ms).
- Zhao Rui 2022 [V]: use plain-column index not functional ones.
- Doc patch 2024 [V]: catalog query to list non-leakproof operators; the practical fix people use is `ALTER FUNCTION ... LEAKPROOF` for custom ops (superuser) [U for exact practice].
- Oracle: per-policy optimizer sees plain predicate text so stats/selectivity work (a benefit of predicate-injection vs subquery) [U].
- Elasticsearch DLS [V partly: https://www.elastic.co/docs/deploy-manage/users-roles/cluster-or-deployment-auth/controlling-access-at-document-field-level]: role query is a normal filter query ANDed into search; multiple roles ORed; no remote lookups (terms lookup) allowed in role queries - same lesson: keep policy local and indexable. Bitset cache for DLS (`xpack.security.dls.bitset.cache.size`, default 10% heap, TTL 2h) [U - not on fetched page; from memory of ES docs]: role query result cached as per-segment bitset and reused across requests; invalidated when segment changes.
How pg_auth does it:
  * Generate the *access path* with the policy: when the permitted set for the subject is small (k <= ~10K ids) emit `id = ANY($array)` (index/bitmap scan, driven from permission side). When large / subject is broad (admin/tenant-wide) emit `tenant_id = $t` (index on tenant) or `true`. Choose per-statement in the hook using cached set cardinality (Oracle-style "predicate chosen at parse time").
  * At install/`pg_auth.protect(table)` time auto-create the supporting indexes (resource id, tenant col, tuple table (subject_type, subject_id, relation, resource_type, resource_id)) and a covering reverse index. Provide `pg_auth.explain()` that warns when a policy col is unindexed.
  * Supply planner support function (`SupportRequestSelectivity` / `prosupport`) on our wrapper functions to give right row estimates; and `CREATE STATISTICS` on (tenant_id, owner_id) for correlated cols.
  * Provide LEAKPROOF operators/functions for the common user-qual types we control; for builtin non-leakproof ops, document the query.

### 1.4 Partitioning
Facts:
- [V source] Only the parent RTE carries securityQuals; children don't (expand_single_inheritance_child). So queries via parent get parent policies only; direct access to a partition gets that partition's policies only (and parent's are NOT applied). pg_auth must apply protection to leaf partitions as well OR forbid direct access (revoke, or hook on every RTE incl. partitions - the hook is called per relation OID: check `rel->rd_rel->relispartition` and apply the parent's model).
- partprune.c has no leakproof/security_level checks (grep over master [V: no matches]) -> pruning with user clauses is not blocked by security level, and since policy quals are in baserestrictinfo they also participate in pruning when they reference the partition key. So: put the tenant/partition-key predicate as a plain `key = const/param` in the policy and you get both *pruning* and index use. A subquery-shaped policy gives no pruning at plan time; runtime pruning happens only for exec Params (initplan-resolved values qualify: initPlan params can drive run-time partition pruning) [U, confirm with EXPLAIN on PG17].
- pg_ivm cannot be used on partitioned tables as base [V README].
Prior art: SQL Server - block predicates unsupported on partitioned views, filter ok [V]. Snowflake - cluster by policy columns [V]. ClickHouse - row policies are a filter condition per table merged into the query, partition/primary-key pruning works since filter is added to WHERE [U, https://clickhouse.com/docs/en/operations/access-rights#row-policy-management].
How pg_auth does it: (1) hook applies the same generated qual for every partition OID found (child or parent) = no bypass; (2) shard/tenant-aligned partitioning: make the leading policy conjunct `tenant_id = <const>`; (3) permission tuple table partitioned by same tenant key (hash/list) so lookups prune too.

## 2. Oracle VPD / Real Application Security  [mostly U, see note]
- VPD: DBMS_RLS.ADD_POLICY; policy function returns predicate string appended to statement; five policy types (above). Numbers: none found. Cost model: DYNAMIC causes policy function execution on each statement execution; STATIC/SHARED_STATIC once; CONTEXT_SENSITIVE re-runs when context (SYS_CONTEXT) values change.
- RAS: principals (users/roles), data security policies = data realms (a predicate over table rows) + ACLs granting privileges to principals on realm; at runtime the realm predicate is ANDed with an ACL check. Scale claims: Oracle states RAS evaluated in the kernel with ACL cache [U]. Fetch https://docs.oracle.com/en/database/oracle/oracle-database/19/dbfsg/ before citing.
- Takeaway for pg_auth: (a) Policy-type taxonomy maps cleanly to Postgres plan-cache behaviour: STATIC = plan-cacheable no subject dependence; CONTEXT_SENSITIVE = depends on `pg_auth.subject` GUC; DYNAMIC = depends on row data/time. Implement the same three classes and set plan invalidation accordingly. (b) Realm + ACL = data-domain predicate separated from principal->privilege table; exactly our "model compiles to predicate over tuples".

## 4. Academic
- **Rizvi, Mendelzon, Sudarshan, Roy, "Extending Query Rewriting Techniques for Fine-Grained Access Control", SIGMOD 2004** [U, from memory]: Truman model (silently rewrite query to run over the user's authorized view; answers may be misleading) vs non-Truman (only execute queries that are provably answerable from authorized views, else reject). Introduces testing *conditional/unconditional validity* of query using authorization views. RLS = Truman. Relevance: if pg_auth wants "reject vs filter" semantics for specific tables, non-Truman is expensive (query containment) -> not for v1. Authorization views with parameters ($user_id) = our compiled predicate.
- **Multiverse databases** (Marzoev, Araújo, Schwarzkopf, Kaashoek, Morris, Kohler, HotOS 2019) [U; the PDF URL I tried 404'd - fetch https://dl.acm.org/doi/10.1145/3317550.3321423]: per-user universe = materialized dataflow of policy-filtered data in Noria; reads hit the precomputed universe; policy enforced on write path into the universe. Costs: memory/space per active universe, write amplification (each write flows to every universe that can see it), mitigations: share computation across universes, lazy/partial materialization, group universes (groups of users share). Takeaway: precompute *who can see what* incrementally. pg analog: IVM'd per-subject (or per-group) effective-access tables; shared "group universes" = materialize at group level (roles/teams) not per user.
- **Qapla** (Mehta et al., NSDI 2017) [U]: policy-compliance enforcement via a database proxy that rewrites queries (policy = SQL queries over columns/rows with purposes); uses query rewriting at proxy; not DB-native, so violates our constraint; ideas: policies as parameterized views + per-column.
- **Blockaid** (Zhang et al., EuroSys 2022) [U]: proxy that checks SQL queries against view-based policies using SMT solver (compliance checking), with a decision cache/"decision templates" generalizing past allow decisions - so most checks are cache hits. Reported overhead ~ few ms median on Rails apps [U numbers]. Not DB-native; transferable idea: cache decisions keyed on *templates* of query shape + context.
- **Sesame** (Kohler lab, SOSP 2024) [U]: privacy-compliant app framework (type-level, app-side). Not applicable.
- **Scooter & Sidecar** (Albert et al., PLDI 2019?) [U]: verified schema migration w.r.t. policy; compile-time checking that migrations preserve policy. Applicable only as a CI check of model changes.
- **ESTRELA** [U: not verified what exactly this is; likely a policy enforcement framework from the multiverse/Qapla line]. Skipped.
- Incremental view maintenance:
  - pg_ivm [V https://github.com/sraoss/pg_ivm]: incrementally-maintained materialized views via AFTER triggers with transition tables. Supports inner/outer joins, DISTINCT, count/sum/avg/min/max, simple EXISTS in WHERE, simple non-recursive CTEs. NOT supported: recursive CTEs, window fns, UNION, partitioned/inherited base tables, views as base. README pgbench (10M rows): plain matview single-row UPDATE 9.05 ms vs IMMV w/ unique index 15.4 ms (+~6 ms); IMMV w/o index 3,224 ms; full REFRESH 20.6 s. Locking: base-table modification takes ExclusiveLock on IMMV under READ COMMITTED (updates serialize); insert-only single-table: RowExclusiveLock. RLS policies added after creation not applied until refresh. => good for one- or two-hop flattening (direct grant tuples join group-membership), unusable for recursive nesting and serializes writers.
  - Materialize / Feldera (DBSP) / Differential Dataflow [U numbers]: external engines, true recursive IVM (iterate to fixpoint), sub-ms update propagation; Postgres integration by logical replication out and writing back results -> eventually consistent, breaks "same-transaction" guarantee unless fenced. SpiceDB Materialize (AuthZed) is this approach [from design.md].
  - Zanzibar "Leopard" index [U, Zanzibar paper USENIX ATC 2019]: precomputed flattened group->member sets for nested groups, using skip lists and incrementally maintained (offline build + incremental layer); the main-memory index serves set ops (union/intersection) of ids; staleness handled with zookies. Directly analogous to roaring-bitmap effective-membership.

## 5. Graph-reachability for nested groups / hierarchies

| Technique | Query cost | Write cost | Memory | Fit |
|---|---|---|---|---|
| Recursive CTE per query | O(reachable) per row/stmt; not indexable via planner except as CTE scan; optimization fence-ish | none | none | fallback; avoid inside RLS qual per row |
| Transitive closure table (materialized `member_of*`) | 1 indexed lookup | insert/delete edge touches |anc|x|desc| rows; deletes need counting (path count / "derivation count") or DRed | O(sum of reachability) can blow up on dense DAGs | best for shallow/medium groups; maintain by triggers or in-extension code |
| Interval / pre-post order labeling (tree) | 2 comparisons | re-label subtree on insert (use gaps / ORDER-maintenance / ltree-like) | O(n) | trees only (folder hierarchies, org units); DAG needs extra "non-tree edges" |
| ltree / materialized path (`ltree`, GiST/btree) | `path <@ 'a.b'` indexable with GiST | moving a subtree rewrites paths | O(n * depth) | trees; built in contrib [https://www.postgresql.org/docs/current/ltree.html] |
| 2-hop labeling (Cohen et al. 2002; PLL / pruned landmark labeling, Akiba 2013) [U numbers] | Lout(u) intersect Lin(v) != empty: sorted-list intersection, ~O(label size) | dynamic updates are hard (incremental variants exist but complex) | O(n * avg label) typically small for real graphs | static-ish graphs; heavy to implement in SQL; could live in an extension as an int[] column + `&&` / GIN |
| Roaring bitmap of reachable ids per node/group (pg_roaringbitmap [V https://github.com/ChenHuajun/pg_roaringbitmap]) | `rb_contains`/`@>`, set ops `&`,`|`; GIN index on `&&`,`@>`; `rb_build_agg` to materialize; compresses dense id sets | rewrite bitmap per changed group (rb ops are O(container)); cascade for ancestors | very compact for dense ids | great for "set of resource ids a subject can read" or "set of subjects in group". No stats collected [V]; btree index fails above ~2.7KB, use GIN/hash [V]. 32-bit ids needed -> map uuids to dense int surrogate (`pg_auth.id_map`) |
| Leopard-style (Zanzibar) [U] | set ops on flattened membership lists | incremental layer + periodic rebuild | in-memory skiplist | the design to copy for large nested groups |

Cost notes for TC maintenance: insert of edge (a,b): for all x in anc*(a) U {a}, y in desc*(b) U {b} add (x,y) with refcount++; delete: refcount-- and remove at 0 (counting algorithm; correct for DAGs, needs path counts). Write amplification = |anc|*|desc| per edge; pathological for large groups inside large groups; cap depth / reject cycles. [U numbers none found; algorithm standard].

## 6. Concrete pg_auth implementation plan, by mechanism

A. **Hook**: keep `row_security_policy_hook_permissive/restrictive` (rewriter-time) to inject quals. Emit quals as Node trees directly (no function call): Const/Param subject, `ScalarArrayOpExpr` over a Param bound to an InitPlan-able `ArrayExpr`/SubLink(ARRAY), or `EXPR_SUBLINK/EXISTS_SUBLINK` against indexed effective-permission table. Apply to partitions too.
B. **Plan-cache / context classes** (Oracle VPD analog): STATIC (no subject dependence, e.g. public rows), CONTEXT_SENSITIVE (subject GUC), DYNAMIC. Use invalidation callbacks (`CacheRegisterRelcacheCallback`/inval on tuple table) to invalidate plans only when relevant tuple/model rows change... careful: if subject baked into Const, plan is per-subject; with Param it's generic.
C. **Effective-permission materialization** (the biggest win; Multiverse/Leopard/Materialize idea, DB-resident): table `pg_auth.effective(subject_id, res_type, res_id)` or roaring bitmap per (subject_or_group, res_type, relation). Maintained (i) synchronously by triggers + counting TC for shallow models (consistent in same txn, preserves "no new enemy" guarantee in design.md), (ii) asynchronously via background worker for deep/recursive models (bounded staleness, expose watermark; fail-closed option: if stale for subject, fall back to live recursive CTE). pg_ivm is usable only for non-recursive flattened views (1-2 hops), and serializes writers.
D. **Auto-index & advisor**: create/verify indexes, warn on policy shape (function calls over row, nested RLS, non-leakproof ops).
E. **Leakproof strategy**: own functions LEAKPROOF (carefully), generated quals use only leakproof ops on user-visible columns; document upstream patch "relax per-role leakproof" as optional; consider `SET LOCAL` ... no.
F. **Partition-aware**: apply per leaf; tenant key first conjunct for pruning.
G. **Planner hooks (stretch)**: `set_rel_pathlist_hook` to add a path driven from the permission bitmap (bitmap-driven index scan: expand rb to TIDs/ids) and `get_relation_info_hook` for stats; upstream-style patch to pull up sublinks in securityQuals.

## 7. Ranking (expected impact for pg_auth)
1. Precomputed effective permissions (flatten nested groups, TC or roaring) so policy = one indexed lookup/ANY; (Leopard/Multiverse/Materialize) - removes recursion + most join cost.
2. Subject-resolved-once predicate generation with plan-context classes (Oracle VPD; Supabase initPlan: 100-10,000x in their benchmarks) + inline/no-opaque-function shape.
3. Policy shape that is indexable and partition-prunable (tenant key conjunct, `= ANY(array)`), auto-indexes (Supabase 171-><0.1 ms).
4. Leakproof discipline + LEAKPROOF own functions (unlocks index use of user quals).
5. Nested-RLS avoidance on pg_auth tables (security definer / owner-run lookups).
6. Planner hooks to semi-join/bitmap-driven scans (high effort).
7. pg_ivm for shallow derived tables; Materialize/Feldera for deep recursion (async, breaks atomicity).
8. Proxy-based approaches (Blockaid, Qapla) - violate DB-enforced constraint; borrow decision-cache idea only.

Open items to verify before building: PG17/18 behaviour of InitPlan params in runtime partition pruning; whether hook-injected SubLinks get hashed subplan vs. ANY index scan; Oracle RAS internals; BigQuery/Databricks/Cockroach/ClickHouse specifics; Blockaid/Qapla/Multiverse numbers.
