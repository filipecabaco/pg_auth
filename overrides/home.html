Your app's permissions, enforced by Postgres. No backend.

Your app talks to Postgres directly, through an API like PostgREST, with no server of its own. pg_auth makes Postgres show each user only the rows they may see. Below, Anne and Bob use the same app, and Anne gives Bob access by writing one row.and Bob sees a document once Anne publishes it.

The rules live in an authorization engine, a service running next to Postgres (here OpenFGA). The documents table points at it with one line:

select authz.protect('documents',
  type => 'document', id => 'id',
  read => 'viewer', write => 'editor');
select authz.protect('documents',
  type => 'document', id => 'id',
  read => 'read', write => 'update',
  attributes => array['owner', 'status']);

The rules: an organisation's members read its documents, and only its admins edit them. Anne is the admin of org 1, which owns three documents. Bob is in no org yet.

Write each rule once, not in every table

Who may read a document? Members of its organisation, and anyone it was shared with. Here is that one rule, both ways.

Row level security, by hand

A policy per operation, on every table that needs the rule.

create policy read on documents
  for select to authenticated
  using (
    exists (select 1 from memberships m
            where m.org_id = documents.org_id
              and m.user_id = (select auth.uid()))
    or exists (select 1 from shares s
               where s.doc_id = documents.id
                 and s.user_id = (select auth.uid())));
-- then update, insert and delete,
-- and again for comments, files, …

pg_auth

  1. Say who is a viewer, once, in the engine's model:

    type document
  relations
    define org: [org]
    define shared_with: [user]
    define viewer: shared_with or member from org

  2. Point each table at it:

    select authz.protect('documents',
  type => 'document', id => 'id', read => 'viewer');

Sharing with a team or adding a role is a change to the model, or a row in a table. There is no policy to edit. Protecting tables

Ask why a row is hidden

Row level security (Postgres's per-row access rules) hides rows without a word. authz.why says who Postgres thinks is asking, and which permission is missing. In the demo's data, after Anne added Bob to org 1, a database administrator asks why Bob still cannot see document 4, which belongs to org 2: 

select * from authz.why('documents', '4', as_subject => 'user:bob');
stepokdetail
subjectyesuser:bob (pg_auth.as_subject: an administrator acting as this subject)
row level securityyeson, forced: the table owner is checked too
rowyesid = 4 exists
policy pg_authnouser:bob lacks document#viewer on document:4; writes need document#editor
verdictnohidden from user:bob: no pg_auth policy allows it

Postgres's answer, with its t and f shown as yes and no. authz.doctor() checks the whole setup and prints the statement that fixes each problem. Inspect and debug

The row level security mistakes you cannot make

A view that leaks
Policies are forced on the table's owner, and the subject comes from the request, not the role running the query.
Policy recursion (42P17)
pg_auth's policy reads only the row, so it cannot recurse into another table's policies.
A partition queried directly
Every partition gets the policy, including ones created later.
A writer who cannot find their own rows
By hand, an update with no matching read policy changes 0 rows without a word. Read and write permissions are installed together, so whoever may write a row can find it.
A spoofed identity
The request cannot set its own subject, and with no subject there are no rows.
An engine that is down
Queries fail rather than guess: no row is shown because nobody could answer.

What it shares with row level security, where Postgres sets the rules: superusers and BYPASSRLS roles skip every policy, and so does a SECURITY DEFINER function they own. An identity set for a whole session on a pooled connection outlives its request; set it with SET LOCAL, as PostgREST does. Every issue, checked

What to expect

A protected query costs about what a well-written policy does

Measured on {{ bench.scenarios }} scenarios taken from problems people hit with row level security, each against its best-practice policy, over {{ bench.pairs }} query and subject pairs: {{ '%.2f' | format(bench.ratio) }}x its planning and execution time overall. Statements that finish in well under a millisecond pay for pg_auth's planning work, so expect those to take somewhat longer.

A grant shows within tens of milliseconds

A membership or a share written as a row showed to its subject 4 to 34 ms after the commit, measured against OpenFGA and SpiceDB: pg_auth tells every session to ask again. A change made in the engine itself, outside Postgres, shows within the sidecar's one-second cache.

When the engine is down, queries fail

Statements on protected tables fail rather than guess: at once if the engine refuses the connection, after 4 seconds (configurable) if it hangs. Answers cached in the last second still serve. Grants written as rows wait and are delivered when it is back.

It needs a sidecar next to Postgres

Postgres 15 to 18 with shared_preload_libraries, and the sidecar on the same host: servers you control. Hosted Supabase and most managed Postgres do not allow that yet.

It is experimental

Pre-release, built from source, no license chosen yet. Every engine is checked for parity against its own answers, and the tests run on Postgres 15 to 18. How it is tested

Pick the engine that fits your rules

EngineDecides onGood for
OpenFGArelationshipssharing, teams, orgs, folders: who is related to what
SpiceDBrelationshipsthe same model, with SpiceDB's schema and consistency
Cerbosthe row's fields and the user's rolesowners, statuses, departments: rules over attributes

Postgres speaks one small protocol to a sidecar on a Unix socket, so changing engines does not touch the database.

Try it on your own Postgres

Build the extension, preload it, run the sidecar next to Postgres pointed at your engine, and protect a table.

Getting started 
# the pinned toolchain, then build into the active Postgres
mise install
cargo pgrx install --release --pg-config "$(which pg_config)"

-- postgresql.conf: shared_preload_libraries = 'pg_auth'
create extension pg_auth;
alter system set pg_auth.sidecar_socket = '/run/pg_auth/default.sock';
select pg_reload_conf();
select authz.configure(subject => 'jwt');
select authz.protect('documents', type => 'document',
  id => 'id', read => 'viewer', write => 'editor');
